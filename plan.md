# Jarvis — architecture & roadmap

Multi-tenant property management. An `Organization` owns `Property` → `Unit` → `Lease`. A `User` joins an org through a `Membership`, which carries an org-scoped `Role`. Tenants are not a separate model — a lease points at the tenant's `Membership`.

An `Organization` also owns its `LeaseTemplate`s — the contract wording a real lease is rendered into. Templates carry `{{placeholder}}` tokens; the token set and its resolvers live in `lib/lease-placeholders.ts`, and `generateLeaseContract` fills them from the lease, its tenant's `MemberProfile`, the unit, the property and the Owner-role member.

## Decision log

| Date | Decision | Why |
|------|----------|-----|
| 2026-08-31 | **Domain email goes to owners only**; auth email follows credentials, not role | Two different questions were being answered by one recipient list. A lease, a renewal, an expiry and an overdue invoice are things the *landlord* acts on, and a tenant onboarded by staff never asked to hear from this app — so the five `…ToTenant` senders are gone and `tenantEmail` is off the mail fact types entirely, which makes "no tenant address exists in the mail layer" structural rather than a convention someone re-breaks. The seven auth emails are unchanged and stay addressed to whoever owns the account, because they are about a login, not a tenancy: a created tenant has `passwordHash: null` and can trigger none of them, and the same person becomes eligible the moment they accept an invitation and set a password |
| 2026-08-27 | The backfill **publishes events**; it does not render | It needs no browser, runs anywhere, and leaves the worker as the only thing that makes a PDF. A script that rendered directly would be a second code path filing contracts — subtly divergent within a month, and the one nobody tests. The cost is that finishing means "queued", not "done", which the script says out loud rather than blocking on something it cannot know |
| 2026-08-27 | Generate is back, **conditional on there being no contract** | Phase 81 removed it because it duplicated the event — true when a contract exists, false when one doesn't, where the tab was otherwise a dead end. Showing it exactly when there is something to recover from keeps the normal case uncluttered and the broken case escapable, which is what "no need for the button" actually meant |
| 2026-08-30 | No template is no longer a dead end: the worker **creates the standard starter** and files it as the default | An organization's first lease used to generate nothing, correctly un-retried, with no on-screen link between the missing PDF and a settings page nobody had visited. `ensureDefaultLeaseTemplate` writes the same `starterBody` the editor offers, marked provisional in its own description. An org that has templates but no default gets its oldest promoted instead — it has already written its own wording, and generating from a starter nobody chose would be worse than the gap |
| 2026-08-30 | Migration drift closed by **deleting the orphans, not recreating them** | Two migrations were recorded in the dev database with no directory in `prisma/migrations`, left by the abandoned `documents` branch along with its `Attachment` table — modelled nowhere, referenced by no code. Recreating the missing files would have preserved a table the schema says should not exist; a fresh database created by these 24 migrations never has one. Dropping the table and its two bookkeeping rows is what makes the two agree, and it is what `prisma migrate dev` would have generated anyway had it been able to run |
| 2026-08-30 | Contract progress reverted: **no `ContractJob` table** | The status row would have been the only way to name a step for a specific lease, since the worker is a separate process and nothing else is shared. Judged not worth a migration — the tab is back to showing the contract when it exists and a Generate button when it does not, and "why is it empty" stays a question for the worker's log |
| 2026-08-27 | Contract is **its own tab**, split from Documents on the type id | The same reason a property splits Images from Documents: one holds what the system produced, the other what people file, and mixing them puts an Upload button beside a row nobody uploads. Split on `LEASE_CONTRACT_TYPE_ID` rather than a new `isGenerated` column — the property split uses `isPhoto` because several types share it, whereas exactly one lease type is machine-made and a constant already says so |
| 2026-08-27 | `DocumentsPanel` grows **`allowUpload`** instead of the Contract tab growing its own table | The checklist rows and the toolbar button are the panel's *invitation to upload*; on a generated list that invitation is a dead end. Turning them off is one flag, and it keeps view / download / delete on the identical code path — a second table for one document is exactly the drift the shared panel exists to prevent |
| 2026-08-27 | Opening upload **from a row locks the type**; from the toolbar it does not | The row already said what it is for. Leaving the field editable there means a click on "Signed agreement" can quietly file a termination notice. Shown disabled rather than hidden, the same call `PhotoUploadDialog` made — the field still says what is being filed. Derived from `initialAssetTypeId !== null`, which already means "opened from a type's own row", rather than a second prop that could disagree with it |
| 2026-08-27 | No **Generate contract** button; the event is the only path | Two ways to do one thing means the tab has to explain which is authoritative. `lease.created` already produces the contract, so the button was a redundancy that would drift. The endpoint stays for backfills and retries — with the honest cost that a lease which missed its contract now has no on-screen recovery |
| 2026-08-27 | Domain events get **their own exchange**, `jarvis.events`, not `jarvis.emails` | The mail queue binds `#` and its consumer treats every message as a finished `MailMessage` to send. A domain event published there is mailed to nobody and dead-lettered. The two carry some identical routing keys (`lease.created`) precisely because they describe the same occurrence in different vocabularies — "tell these people" versus "this is now true" — and that overlap is the trap, not a reason to share |
| 2026-08-27 | Contract generation is a **queued worker**, not an `after()` in the route | The user's constraint, and the right one: signing a lease must not wait on a browser launching or fail because object storage blinked. The lease commits, the event goes on a durable queue, and a worker outage becomes a delay rather than a set of leases with no contract and no record of why. It also confines Chromium to one process — `POST /api/leases/[id]/contract` publishes rather than rendering, so the web app never needs a browser installed |
| 2026-08-27 | PDF via **Chromium (Playwright)**, not a pure-JS generator | The contract's look is already defined in `lib/lease-document-style.ts` and already approved by whoever wrote the template in the editor's Preview. pdfmake and friends re-implement layout, so the stored contract would *approximate* the preview and nobody could say which was authoritative. Chromium renders the same stylesheet — the PDF is the preview. Cost, stated plainly: a ~100MB browser on the worker host |
| 2026-08-27 | A generated contract goes through **`createDocument`**, the same door as every upload | The ask was records "consistent as how we keep our records". The only way to mean that is to reuse the path: same object-key convention, same duplicate rules, same `FileAsset` shape, same list/download/delete code. A parallel table for machine-made files would have diverged within a month. It cost one change — `userId` became nullable, because a worker is not a person and `uploadedById` should say so rather than name a membership that did nothing |
| 2026-08-27 | Retries **republish with an `x-attempts` header**; unfixable messages are acked, not retried | `nack(requeue: true)` returns a message that looks brand new, so a poisoned one loops forever at prefetch 1 and every later lease waits behind it. Carrying the count makes the retry terminate. And "this organization has no template" is a normal state, not a fault — retrying it forever would bury a real failure in noise, so it acks and the Contract tab's Generate button is the recovery |
| 2026-08-26 | Removing the bottom Cancel/Save row meant **Save could no longer be conditional on `isDirty`** | It was the page's only other way to submit. Gating the lone remaining Save button behind "something changed" would have made an untouched brand-new template — the common case for a first-ever template — impossible to create without editing it first. Save is now always present; only Reset (meaningless with nothing to reset) stays conditional |
| 2026-08-26 | Unsaved-changes tracking uses a **lazy `useState` baseline, not a `useRef`** | The new React Compiler ESLint rule (`react-hooks/refs`) rejects reading `ref.current` during render, and `isDirty` has to run every render to decide whether to show the top bar. `const [baseline] = useState(initialValue)` gives the same "set once, stable forever" value a ref would, but as a normal render-safe read — no eslint-disable needed, unlike the ref-based first draft |
| 2026-08-26 | Table borders are **explicit CSS**, not a default anyone was relying on | A plain `<table>` renders with no visible border in every browser — inserting one and seeing "nothing" was never a bug in the insert, just an unstated assumption about what HTML gives you for free. `.jarvis-doc table td/th` now carries a real `1px solid #999`, with the signature block's `.signatures` table explicitly exempted since it was designed around the `.rule` underline, not a grid |
| 2026-08-26 | List bullets/numbers needed **restating** inside `.jarvis-doc`, because Tailwind's Preflight had already removed them | `list-style: none` on every `ul`/`ol` is part of Tailwind's base reset, applied to the whole app — including the editor's `contenteditable` surface, which lives on the app's own page. The preview iframe is a separate document Tailwind never touches, so the bug was invisible there and only showed while editing. Fixed by restating the browser default explicitly, scoped to `.jarvis-doc` so nothing outside the document surface changes |
| 2026-08-26 | Edit/Preview is **one alternating button**, and the sample-data switch exists only in preview | Two tabs plus a mode pair above the paper was three controls for two decisions. One button carries the mode, and the second appears only where its question is meaningful — asking "sample data or placeholders?" while someone is typing is a control that cannot do anything |
| 2026-08-26 | What a template *is* — name, language, description, **and whether it is the default** — all lives in the details dialog | The default checkbox was the last of those four sitting in the editor, under a card of its own, competing with the contract. Grouping them puts every once-a-lifetime decision in one place and leaves the page to be a document. It also means the create flow captures the default before the editor is ever reached, rather than after the contract is written |
| 2026-08-26 | The editor stores `{{tokens}}` and displays **chips**, converting at the boundary | `tokensToChips` on the way in, `editorHtmlToBody` on the way out. Keeping the stored format exactly as it was meant the API, the renderer, the preview and contract generation needed no changes to gain a WYSIWYG editor — the whole feature is two functions and a component. The alternative, storing the editor's own DOM shape, would have put an editor's implementation detail into the database and into every contract ever generated |
| 2026-08-26 | `contenteditable` + `execCommand`, **not** ProseMirror | Nothing in the project has an editor library and a lease template needs formatted prose, a table and some variables. `execCommand` is deprecated-but-universal, and the honest trigger for replacing it is written down: comments, revision marks, collaborative cursors, or reliable undo grouping. Adding six packages before any of those exist buys complexity, not capability |
| 2026-08-26 | The editor surface is **uncontrolled**, seeded once | A controlled `contenteditable` rewrites `innerHTML` on every render, which puts the caret back at the top of the document on every keystroke. State flows one way — outwards — and `documentKey` is the single escape hatch for a deliberate reseed. The same reason the two tabs are `keepMounted`: unmounting the editor and remounting it would reseed from the original body and silently discard everything typed since |
| 2026-08-26 | Contract typography moved **out of the body** into `lib/lease-document-style.ts` | A `<style>` block at the top of the body was reasonable while the body was edited as HTML. Inside a WYSIWYG editor it is a screenful of CSS above the agreement that the author can break by deleting a line. One sheet, read by the editor surface and the preview iframe, also means the two cannot drift — which they already could |
| 2026-08-26 | An **unknown** token stays literal text in the editor, where a known one becomes a chip | The chip is a promise that something will fill it in. Rendering a typo'd token as a chip makes a broken variable look identical to a working one, and the mistake surfaces in a signed contract rather than in the editor. Same reasoning as the renderer leaving unknown tokens visible in output |
| 2026-08-26 | A parent nav item with children is **never active**; only the child is | Active means "this is the page you are on", and a parent with children is never that. Lighting both put two pills on screen for one location. `containsActive` still opens the group on arrival — the two ideas were sharing one prop, which is why they had to be separated rather than just restyled |
| 2026-08-26 | **The placeholder list is one Prisma-free module**, imported by the editor and resolved by the server | `lib/lease-placeholders.ts` holds the key, label, group, example *and* resolver for all 27 tokens. Splitting it — a list for the UI, a switch for the renderer — is how you end up offering `{{tenant_nationality}}` in a panel that nothing on the server fills. The context object is plain data built by `buildLeaseContext`, which is what keeps Prisma out of the client bundle without duplicating the list |
| 2026-08-26 | An unresolved token renders a **blank fill line**; an unrecognised one is left **visible** | They are different mistakes. A tenant with no NIDA on file is normal, and a contract with a line to complete by hand is the paper convention already. A token no placeholder defines is a typo in the template, and blanking it hides the error until the contract is signed — so it prints as written and comes back in `unknown` for the preview to flag in red |
| 2026-08-26 | Template bodies are **sanitized server-side *and* rendered in a `sandbox=""` iframe** | The author is a member of the organization, so the trust level is any CMS's — but a tenant reading their own contract should not run a manager's script. The regex allowlist is not a parser and cannot be the only defence; the sandbox is what actually disables execution. `?format=html` adds `Content-Security-Policy: sandbox; default-src 'none'` for the one route that hands a body to a browser as a document. The iframe also stops a template's page-wide CSS leaking into the app, which is why `<style>` can be allowed at all |
| 2026-08-26 | **Exactly one default template while any exist** — it moves by promotion, never by demotion | An organization with templates and no default makes `GET /api/leases/[id]/contract` 404 for a reason nothing on screen explains. So the first template is always the default, the current one cannot be unchecked, and deleting it promotes the oldest survivor. The form *shows* this with a checked, disabled checkbox rather than letting the server silently overrule what was submitted — the first version did the latter and the box simply appeared to do nothing |
| 2026-08-26 | Changing the language swaps the starter body **only while it is still an untouched starter** | A blank HTML box beside a token list is a format, not a contract, so New opens on a real ten-clause agreement. But the moment a word of it has been edited it is someone's work, and replacing that because a dropdown moved would be the worst bug this page could have — `isStarterBody` compares against the exact starters, so one typed character ends the swapping forever |
| 2026-08-26 | Caret restoration after inserting a token lives in an **effect, not a `requestAnimationFrame`** | The textarea is controlled: the rAF fired before React committed the new value, so `setSelectionRange` ran against the old one and the caret ended at 0 — a second insert landed *before* the first. The position is held in a ref and applied from an effect keyed on the body, which runs after the commit. This is the same class of bug as any "read the DOM right after setState" |
| 2026-08-26 | `SidebarMenuSubButton`'s **active colours were fixed in `components/ui/sidebar.tsx`**, not overridden per-call | shadcn pairs `bg-sidebar-accent` with `text-sidebar-accent-foreground`; in this theme those are a mid blue and a gold, so the first submenu the app ever had rendered an unreadable label. Same shape as the `checkbox.tsx` border fix — the theme's token pair is wrong for the job, so the component uses the pair that works (`primary`/`accent`, matching its own parent button) with a comment saying why. A per-call `className` would have left the trap for the next submenu |
| 2026-08-25 | Profile photos are fetched **in one batched query per list**, never per row | `getProfilePhotoIds(organizationId, membershipIds[])` takes the whole set of ids a table or panel is about to render and returns one `Map` — the Tenants table, the Users table, and all three membership-touching dashboard panels each call it exactly once. The alternative (a lookup inside `PersonCell` itself, resolved per row) would have been the simpler diff and the N+1 nobody notices until the table has fifty rows |
| 2026-08-25 | The crop dialog's frame is **square with two stacked copies of the image**, not a circle clipping one | The first version clipped the container to a circle outright, which meant the part about to be cropped away simply vanished — no warning if a face or a logo sat near the edge. Duplicating the image (one blurred+dimmed filling the square, one sharp clipped to a circle on top) keeps that content visible as context instead of hidden, at the cost of one extra `<img>` tag reading the same `src` from the browser's own cache — no second network fetch |
| 2026-08-25 | **`isPhoto` no longer forces `allowsMultiple`** — reverted from Phase 71 | The forcing existed so a hand-edited or badly-seeded gallery type couldn't refuse a second photo. It broke the moment a legitimately *singular* photo type existed — `PROFILE_PHOTO`, seeded this phase — by silently letting a second profile photo upload through with no delete, a real bug caught in verification, not a hypothetical. `allowsMultiple` is the single source of truth now, in both `createDocument`'s duplicate check and `createAssetType`'s default; every type that existed before this already carried the correct value, so nothing else changed behaviour |
| 2026-08-25 | The profile photo crop dialog is **hand-built on a canvas**, not a library | The entire feature is drag-to-pan plus zoom-to-a-fixed-square — a pointer handler, a range input, and one `drawImage` call cover it. A dependency would buy configurability (aspect ratios, output formats, rotation) this app has no use for; `photo-crop-dialog.tsx` is under 250 lines total for it |
| 2026-08-25 | Uploading a profile photo **deletes the old one first**, client-side | `PROFILE_PHOTO` is singular, so a second upload without deleting 409s. Surfacing that error to someone who just wants to change their photo would be a worse experience than the alternative: delete, then upload. The accepted trade-off is narrow and written down — if the upload fails after the delete succeeds, the member is briefly back to initials and has to retry, rather than the old photo silently surviving a failed replace |
| 2026-08-25 | **The photo dialog lost its type picker entirely** | Every subject has exactly one photo type, so a dropdown was a control that did nothing until opened, existing only to host an "Add a type…" nobody had asked for on this surface. The field now shows the type, disabled — present so its existence isn't hidden, inert because there is nothing to decide. The trade, written down rather than silently accepted: an organization that wants a *second* photo category has no UI path to one anymore, only the API directly |
| 2026-08-25 | **`isPhoto` forces `allowsMultiple` in two places, not one** | `createAssetType` already set it at creation; `createDocument`'s duplicate check now also reads `!assetType.allowsMultiple && !assetType.isPhoto` rather than trusting the stored flag alone. Belt and braces on purpose — a gallery that rejects a second photo because a row was hand-edited or seeded wrong is a worse failure than a redundant check |
| 2026-08-25 | Adding a document type asks **"allow multiple", defaulting to unchecked** | Most invented types name one specific paper — a certificate, a report — not a collection. Defaulting to single is the fewer-surprises choice: a 409 on a second upload is recoverable (delete the old one, or check the box next time), while a duplicate nobody meant to allow just sits there. The checkbox replaces the caption that used to explain organization-scoping and filing location, which the picker's surroundings already made obvious |
| 2026-08-25 | **Tab count badges hide at zero**, everywhere this session touched | Already the rule on the Billing and Users tabs, unapplied to the newer Units/Images/Documents/Lease badges until now. "A 0 beside a tab reads as a problem rather than as a total" — bringing the newer tabs in line closes a consistency gap rather than inventing a new convention |
| 2026-08-25 | **Document types are rows, not a Prisma enum** | The enum grew three times in two days and each growth was a schema change, a migration, a client regeneration and a dev-server restart to add one string. Every organization runs on slightly different paperwork, so the list was never going to hold still. The seventeen values are seeded as `isSystem` rows shared by every tenancy, which is also what let the old column be backfilled by key rather than by hand |
| 2026-08-25 | The migration is **hand-written**, and refuses to continue if the backfill misses a row | `migrate diff` generates exactly the right shape in exactly the wrong order — drop the old column, add a `NOT NULL` new one, nothing in between. Seed → backfill → enforce → drop keeps every row typed throughout, and a `DO $$` block raises with a count if anything failed to match, because the alternative is a NOT NULL violation that names no row and no reason. The old enum is renamed out of the way first: Postgres will not hold a type and a table of the same name |
| 2026-08-25 | **The group is never asked for** — `subject` and `isPhoto` come from the surface, not the person | A dropdown on a lease already knows it is standing on a lease; the Images tab already knows it is a photo. Presenting a taxonomy at the moment someone is trying to upload a file is precisely the friction that made the enum feel rigid. The grouping still exists, and is still what decides which dropdown a type appears in — it is just inferred rather than requested |
| 2026-08-25 | **Custom types are scoped to one organization**; system types are shared and immutable | A type invented by one tenancy appearing in another's dropdown would leak how that business operates, which is the same boundary every file already respects. System rows carry a null `organizationId`, which needs a *partial* unique index to stop two of them sharing a key — Postgres treats NULLs as distinct and Prisma cannot express a partial index, so it is hand-written beside the composite one |
| 2026-08-25 | `FileAsset.assetTypeId` is **`RESTRICT`**, not cascade | Every other foreign key on `FileAsset` cascades because deleting the subject makes the file meaningless. A *type* is different: deleting "Title deed" does not make the deeds meaningless, it makes them unlabelled — and cascading would silently destroy files as a side effect of tidying a dropdown. The database refuses instead, which is why retiring a type will need a flag rather than a delete |
| 2026-08-25 | "Add a type" lives **inside the dropdown**, and the photo picker renders even with one option | A list you can extend only helps if extending it is available at the moment you discover it is missing — mid-upload, holding a file, looking at a dropdown that does not contain it. A settings page nobody visits would leave the enum's real problem in place. It is a button under a divider rather than a `SelectItem`, because selecting one would set the field to a sentinel and a type called `__add__` is one forgotten guard from reaching the API |
| 2026-08-25 | Property photos get **their own tab**, not a band above the documents table | Photos are browsed and papers are filed — two different postures. Stacked in one tab, the carousel pushed the table below the fold on any property that had pictures, and the type dropdown had to exclude photos to stop two routes leading to the same place. Separate tabs make the exclusion structural rather than a filter someone has to remember |
| 2026-08-25 | **`UNIT_PHOTO` is its own enum value**, not a `UNIT_DOCUMENT` with a picture in it | `SUBJECT_FOR_ASSET_TYPE` maps one subject to each type and the UI derives its dropdowns from that map, so "the photos of this unit" has to be answerable by a type filter rather than by inspecting MIME types at read time. Adding a value is one `ALTER TYPE`; teaching every read path to sniff `fileType` is forever |
| 2026-08-25 | **Photos get their own dialog and their own surface**, not a `multiple` flag on the documents upload | Almost nothing survives the change: there is no type to choose, the input is `multiple`, what you review before sending is a grid of thumbnails rather than one file name, and the outcome is per-file — some succeed while others fail. Two components that each do one interaction well beat one with a mode switch. For the same reason the property tab shows photos in a carousel *above* the documents table and keeps the photo type out of that table's dropdown: two routes to the same place, one of which drops the file where you weren't looking, is worse than two clearly separate places |
| 2026-08-25 | Photo uploads are **sequential**, not parallel | Ten phone photos at up to 10 MB each would open ten concurrent requests, each buffering its whole body in a route handler — the presigned-upload note in `lib/storage.ts` is the real fix, and until then serialising is what keeps the ceiling predictable. The visible cost is a tile settling at a time, which is the same progress `ImportDialog` already established |
| 2026-08-25 | `DocumentsPanel` is **one component for every subject**, extracted the moment there was a second caller | The tenant table and a property table would have started identical and drifted — different columns, different delete copy, one of them quietly missing the red delete icon. Extracting at two callers rather than three is the cheapest moment it will ever be. The dialogs moved to `components/documents/` with it: leaving them under `tenants/` while properties imported them would have been actively misleading |
| 2026-08-25 | **`npx shadcn add` is not safe to run unattended here** | Adding `carousel` silently rewrote `components/ui/button.tsx`, reverting the hover-shadow variants this codebase deliberately introduced and documents in comments — a change across every button in the app, arriving as a side effect of adding an unrelated component. It also brought two `react-hooks/set-state-in-effect` **errors**, which this project lints as errors rather than warnings. `AGENTS.md` still says add components this way; the addition is that the diff must be read afterwards and anything outside the requested component reverted |
| 2026-08-24 | **One document per (subject, type)**, unless the type is a declared collection | `NIDA`, *the* signed agreement and *the* invoice are singular by nature — a second upload should replace, not accumulate. `allowsMultiple()` in `lib/document-options.ts` names the exceptions (photos, permits, amendments, renewals, and the two catch-alls `OTHER`/`TENANT_DOCUMENT`) rather than the rule needing one; `createDocument` checks before the upload, the route answers 409, and the upload dialog disables the taken option in the dropdown rather than only rejecting after submit. Enforced in application code, not a DB constraint — the constraint would need a partial unique index over a `COALESCE` of six nullable columns, conditioned on which types are restricted, and the race it would close (two uploads of the same type in the same instant) is not one this app's usage pattern produces |
| 2026-08-24 | Documents render as a **plain `Table`, viewed in a dialog** — not `DataTable`, and not a new tab | The list is usually three rows, so `DataTable`'s search, pagination and column visibility are weight without a job; the four columns are fixed and the `Table` primitives say so directly, the way `payment-accounts-card.tsx` already does. Viewing happens in a dialog over the same `GET /api/documents/[id]` the download uses — it already answers `Content-Disposition: inline`, so there is no blob URL, nothing held in memory, and closing unmounts the frame. A new tab would have meant leaving the member you were reading about. The known cost is mobile: five columns scroll sideways, and only tapping the file name is reachable without it |
| 2026-08-24 | **One `/api/documents` for every subject**, not `/api/tenants/[id]/documents` and five more like it | A document is the same object whether it is a NIDA card or a signed lease: same validation, same key layout, same tenancy check. `subjectType` picks the column. Six sibling routes would mean six places to forget the MIME allowlist, and the second one written would already be a copy of the first. The tenant documents UI is simply its first caller |
| 2026-08-24 | **Bytes pass through the route handler** to the bucket, rather than the browser being handed a presigned URL | A presigned upload is cheaper on the server and is the right answer for large files — but it is also a credential in a query string, and it moves the size and type checks to *after* the object already exists. Passing the bytes through means the file is validated before anything is stored, and `MAX_FILE_BYTES` (10 MB) is set by what a route handler should hold in memory rather than by what the bucket will take. Reads work the same way, which is what keeps the bucket private and every read behind the same organization check as every other route |
| 2026-08-24 | The MIME **allowlist** is matched on the reported type, and the stored extension comes from it — never from the file name | `image/svg+xml` and `text/html` are a picture and a document in ordinary speech and a script as far as a browser is concerned; served back from this app's own origin, that is stored XSS. So: four types in, `X-Content-Type-Options: nosniff` on the way out, and the object named by a fresh uuid with an extension this app chose. A file name is whatever the client felt like sending, `../` included |
| 2026-08-24 | `assetType` is **pinned to one subject** by a table in `lib/document-options.ts`, not by a database CHECK | A CHECK pairing seventeen enum values to six columns would have to be rewritten every time a type is added, and the failure it prevents is a UI problem rather than a corruption. `SUBJECT_FOR_ASSET_TYPE` is `Record<FileAssetType, DocumentSubject>`, so the compiler demands a home for every new type; the upload schema rejects the mismatch, and the tenant dropdown is *derived* from the same table rather than listing the four types a second time. `OTHER` is the one value allowed anywhere, which is what lets every other value be strict |
| 2026-08-24 | The cross-organization rule is enforced in **`createDocument`, before the upload** | Promised in the 2026-08-24 schema entry, delivered here. One query per subject (a Unit reaches its organization through its Property, a Payment through three hops), run before the key is built, so a lease id borrowed from another tenancy resolves to nothing and no object is written. Reads are scoped the same way — `getDocument` filters on `id` *and* `organizationId` in one query rather than fetching by id and checking afterwards, because the check that can be forgotten eventually is |
| 2026-08-24 | Write **object then row**; delete **row then object** | Both orders are chosen so the failure that survives is the invisible one. A row written before a failed upload is a document that will not open; an object written before a failed insert is merely wasted bytes — so uploads write the object first, and a failed insert best-effort removes it. Deleting reverses it for the same reason: a row whose object is gone renders as a broken document, so the row goes first |

## Auth design (current sprint)

- **Credentials**: email (required, unique) or phone (optional, unique) + password. Hash with `bcryptjs` (cost 10). Zod validation, password min length 8.
- **Session**: JWT signed with `jose` HS256, secret in `AUTH_SECRET` env. Stored in httpOnly cookie: `sameSite=lax`, `secure` in prod, 7-day expiry. Payload `{ sub: userId, orgId: activeOrgId | null }`.
- **Helpers** (`lib/auth/`): `hash.ts`, `jwt.ts`, `session.ts` (`getCurrentUser()` / `requireUser()` wrapped in React `cache()`), zod schemas.
- **Flows** (route handlers): `POST /api/auth/register`, `POST /api/auth/login` (identifier resolves as email if it contains `@`, else phone), `POST /api/auth/logout`, `GET /api/auth/me`.
- **Route protection**: `proxy.ts` at repo root (Next 16's renamed middleware) redirects unauthenticated page requests to `/login` and bounces authed users off `/login`/`/register`; API routes enforce auth themselves.
- **Org creation**: happens inside registration — one `$transaction` creates `User` + `Organization` + seeds an `Owner` `Role` + `Membership`, then the session cookie is issued with that `orgId`. Org switcher (re-issue cookie with new `orgId`) deferred until invitations exist.
- **Schema delta** (`auth_fields` migration): `User.passwordHash String`, `User.phone String? @unique`.

## Out of scope (future sprints)

SMS OTP (needs Twilio or similar) · RBAC permission enforcement beyond role seeding · refresh-token rotation.

**Email transport now exists** (Phase 62): RabbitMQ carries rendered messages to a standalone mail service. **Password reset shipped in Phase 63** and **email verification in Phase 64**, so every section-A email now publishes except `auth.login.new_device` (no device tracking to compare against). Sections B–E of the catalogue — invitations, leases, billing, digests — remain unwired, and everything time-based in them still waits on the scheduler auto-renewal also needs.
