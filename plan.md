# Jarvis — architecture & roadmap

Multi-tenant property management. An `Organization` owns `Property` → `Unit` → `Lease`. A `User` joins an org through a `Membership`, which carries an org-scoped `Role`. Tenants are not a separate model — a lease points at the tenant's `Membership`.

## Decision log

| Date | Decision | Why |
|------|----------|-----|
| 2026-08-10 | Editing a lease **re-derives** it from the unit's current rent, and is **refused when the new value falls below what has been paid** | `insertLease` locks the value at signing so later rent changes don't rewrite history; an edit is the opposite case — a correction of a record that was wrong — so it recomputes `endDate` and `leaseAmount` and syncs the invoice in the same transaction. The form shows the recomputed total so it can't change out of sight. The one thing an edit may not do is strand money: payments already recorded would leave an invoice mysteriously overpaid, so that edit is rejected naming both figures. **The overlap check must exclude the lease being edited** — a lease always overlaps itself, and without `id: { not: … }` no edit could ever save |
| 2026-08-10 | Derived-balance queries read **one grouped aggregate**, never a nested `payments` include | `getPayments` included `invoice.payments` per row to show invoice status, so an invoice with n payments hydrated n² payment rows — quadratic in the common case of an instalment plan. A balance can't be filtered or summed in SQL because it isn't a column, but `payment.groupBy` gets it at one row per invoice, and `getPayableInvoices` then pays for its tenant/unit joins only on the rows that survive the filter. Verified behaviour-preserving by capturing the figures in SQL before the rewrite and matching them exactly after |
| 2026-08-10 | A lease can be created from a tenant's own page, with that tenant **locked** into the form; the button is **hidden for non-tenant members** | `LeaseFormDialog` grew one optional `lockedTenantId` prop rather than a second dialog — the property→unit cascade, the minimum-tenure check and the overlap handling are all the same, and a copy would drift. Locking rather than merely pre-filling: a lease created from someone's page that quietly ended up belonging to a different tenant is a trap, not a convenience. Hiding the button for non-tenants matches the server, where `createLease` requires the Tenant role and 404s otherwise — an affordance that can only fail is worse than none |
| 2026-08-10 | **Billing totals live on the dashboard only**; the payments page is a bare ledger, and both it and the lease Billing tab present payments through the same `DataTable` | User call. Metrics were duplicated as summary cards on the payments page and as a bespoke `<Table>` in the Billing tab — two places to keep in step with the dashboard, and two payment tables that had already drifted (one had search and filters, the other didn't). The dashboard's Payments card leads with **outstanding balance** rather than collected: it's the figure that needs acting on. Its `billing` block comes from one `invoice.findMany` including payments, because a balance is derived per invoice and can't be aggregated in SQL |
| 2026-08-10 | **The invoice's figures live on the lease's Overview tab, not its Billing tab**; Billing is only the payment ledger | User call, and the split it implies is the right one: an invoice is part of what a lease *is*, so it sits with the lease terms; what has been paid against it is a log, and a log is what earns a tab. The card is deliberately a `Card` + two-column `DetailRow` `<dl>` — identical in shape to the Lease terms card directly above it — rather than the compact strip it replaced. A distinct treatment would have made it read as a transplant on a tab whose whole convention is label/value rows |
| 2026-08-10 | The payments table shows **no per-payment balance and no view button** | Two things that looked useful and weren't. The balance was the *invoice's* balance as of now, so every payment against one invoice showed the same number in a per-payment row — a figure that invites being read as "left after this payment" while meaning nothing of the sort. The eye button duplicated `getRowHref`'s double-click-to-open, which works with or without it. Deleting is now the only row action |
| 2026-08-10 | **`basis-full`, not `w-full`, is what wraps a flex child onto its own line** | The Billing tab's invoice strip truncated "TZS 750,000" to "TZS 7…" on mobile. `w-full` looked right but `flex-1` sets `flex-basis: 0`, and basis beats width in flex layout — the child shrank instead of wrapping. Only caught by looking at a 375px screenshot; the desktop layout was fine throughout |
| 2026-08-09 | Payment method is a **closed list in `lib/payment-options.ts`**, used by *both* the payments page and the lease Billing tab | The Billing tab originally took free text. Once the payments page gained a method facet filter, free text elsewhere would produce values that filter could never match — "M-Pesa", "Mpesa" and "mpesa" coexisting as three unfilterable methods. `Payment.method` stays a nullable `String` in the schema, so this constrains the form without constraining the column, same as `lib/unit-options.ts` |
| 2026-08-09 | **`lib/invoice-types.ts`** holds `InvoiceStatus`, `deriveInvoiceStatus`, `invoiceReference` and `INVOICE_STATUS_VARIANT`; `lib/invoices.ts` keeps only the Prisma-touching functions and re-exports the rest | The payments table and its dialogs need these as *runtime* values, not just types. Importing them from the Prisma-importing `lib/invoices.ts` would pull `pg` → `require('dns')` into the browser bundle and fail the build — the hazard already documented for `lib/search-types.ts` and `lib/auth/constants.ts`. **The rule for any new `lib/*` shared with a client component** |
| 2026-08-09 | Auto-renew is a **`Switch` that is disabled until a minimum tenure exists**, and clearing the tenure forces it off | The renewal job reads its term from `unit.minTenureMonths` and skips a unit without one — so a unit saved as auto-renewing with no tenure is a setting that silently does nothing. Gating the control makes that unrepresentable rather than leaving it to be discovered when a lease fails to renew. The explanatory caption was dropped as redundant once the control itself enforces the rule |
| 2026-08-09 | Billing is **one `Invoice` per `Lease`**, for the full `leaseAmount`, not recurring monthly invoices; `InvoiceStatus` (Unpaid/Partial/Paid) is **derived** from `amount` vs `Σ Payment.amount`, never stored | User decision, matching the literal request ("generate an invoice, then multiple payments over that invoice") and this codebase's existing derive-don't-store rule for `LeaseStatus`/`TenantStatus`. `createLease` now creates the `Lease` + `Invoice` atomically in `insertLease()` (`lib/leases.ts`); overpayment is rejected server-side in `lib/invoices.ts`'s `recordPayment`. Closes the `lib/dashboard.ts` decision-log item (2026-08-05) that flagged swapping lease-value derivation for real `Payment` rows once the model existed — `getDashboardStats`'s "collected" figure now sums actual payments in the year |
| 2026-08-09 | Lease auto-renewal setting is a **`Unit.autoRenew` boolean**, and it runs **lazily on page load** (`/leases`, `/dashboard`) rather than a cron endpoint | User decision on both placement (per-unit default, not per-lease or a new org-wide Settings page — this app has no settings surface at all) and trigger (no scheduler infra exists yet; matches the "derive on read" philosophy). `runAutoRenewals(organizationId)` in `lib/lease-renewal.ts` finds ended leases on auto-renewing units with no successor (`renewedTo` null) and calls the same `insertLease()` overlap-checked path `createLease` uses, so a unit someone re-let by hand between end-date and page-load can't be double-booked. Renewal duration is the unit's `minTenureMonths`; a unit with `autoRenew` on but no `minTenureMonths` set is skipped, not silently dropped. Idempotent by construction: `renewedFromId` is `@unique`, so a lease can never gain two successors. **Known gap**: a lease only renews once someone loads one of those two pages after its end date passes — no same-day guarantee |
| 2026-08-08 | Record kinds get **one `--kind-*` token each, holding the ink**; badges derive their own tint from it at 10% alpha | A tinted background composites correctly over any surface, so a single token per kind serves both themes and only its lightness is retuned in `.dark` — the alternative, a bg/fg pair per kind per theme, is four values to keep in sync and drifts. Hues are anchored to the existing palette (brand gold, the chart blues/greens/terracotta) with only violet added, so five distinguishable kinds cost almost no new colour vocabulary. **Contrast was measured, not eyeballed**: the first pass passed AA-large but failed AA text at 12px, and `getComputedStyle` returns `lab()`/`oklab()` in this browser, so any check has to resolve through a canvas to get true sRGB |
| 2026-08-08 | Every bulk importer goes through **`lib/xlsx-import.ts`** + the generic `components/import-dialog.tsx`; an entity supplies only its columns and a `toCandidate` mapper | Tenants needed the same flow as units, and the fiddly parts are entirely entity-agnostic — flattening rich-text/formula cells, matching headers loosely, skipping padding rows, catching in-file duplicates, capping rows, and suppressing schema messages the coercion pass already reported. Two copies of that would drift. The unit importer was rewritten onto it and checked against the same 9-row fixture for identical output before tenants were built on top |
| 2026-08-08 | Unit amenities are **free text**, not `z.enum(UNIT_AMENITY_OPTIONS)` | Prisma always stored `String[]`; only the schema made the list closed, so a caretaker couldn't record anything the seed list missed. The options remain as checkboxes — a starting set, not a constraint — with free entry beside them, de-duplicated case-insensitively so typing "balcony" ticks "Balcony" rather than adding a twin. Capped at 40 items × 40 chars so a client can't push unbounded data into the row |
| 2026-08-08 | Spreadsheet columns holding a leading zero are written with Excel's **text format (`@`)**, and the parser restores a stripped one | A phone typed as `0712345678` into a General cell is stored as the number `712345678` — silently, and the import would then reject every row. The format fixes the template; the 9-digit recovery in `tenant-import.ts` covers files that were pasted or rebuilt without it |
| 2026-08-08 | Bulk unit import **parses on the server, creates on the client, one row at a time** against the existing `POST /api/properties/[id]/units` | `exceljs` stays out of the browser bundle (the dialog imports only `import type` from `lib/unit-import.ts`), and reusing the single-unit endpoint means auth, org ownership and the per-property duplicate-label check are the same code the form already goes through — no second implementation to drift. Sequential, not parallel: a duplicate label is only detectable against rows already committed, and one-at-a-time is what the per-row progress list shows. Template generation and parsing both read one `COLUMNS` array, so a column can't be added to one side only |
| 2026-08-08 | **Any schema whose transform emits `null` is `.nullish()`, never `.optional()`** — swept across the codebase | A schema that outputs `null` but only accepts `string \| undefined` cannot re-parse its own output. Fixed in `units-schemas.ts`, then swept: `properties-schemas.ts` (`description`), `member-profile-schemas.ts` (`optionalText`), and **`lib/phone.ts` (`optionalTzPhoneSchema`)**, which the first pass missed because it was found by grepping `.optional()` rather than by asking which schemas emit null. `members-schemas.ts` and `tenants-schemas.ts` were checked and **deliberately left alone** — their `email` transforms to `undefined`, not null, so they were always idempotent; making them `.nullish()` would newly admit `null` and write it to the DB. ## Auth design (current sprint)

- **Credentials**: email (required, unique) or phone (optional, unique) + password. Hash with `bcryptjs` (cost 10). Zod validation, password min length 8.
- **Session**: JWT signed with `jose` HS256, secret in `AUTH_SECRET` env. Stored in httpOnly cookie: `sameSite=lax`, `secure` in prod, 7-day expiry. Payload `{ sub: userId, orgId: activeOrgId | null }`.
- **Helpers** (`lib/auth/`): `hash.ts`, `jwt.ts`, `session.ts` (`getCurrentUser()` / `requireUser()` wrapped in React `cache()`), zod schemas.
- **Flows** (route handlers): `POST /api/auth/register`, `POST /api/auth/login` (identifier resolves as email if it contains `@`, else phone), `POST /api/auth/logout`, `GET /api/auth/me`.
- **Route protection**: `proxy.ts` at repo root (Next 16's renamed middleware) redirects unauthenticated page requests to `/login` and bounces authed users off `/login`/`/register`; API routes enforce auth themselves.
- **Org creation**: happens inside registration — one `$transaction` creates `User` + `Organization` + seeds an `Owner` `Role` + `Membership`, then the session cookie is issued with that `orgId`. Org switcher (re-issue cookie with new `orgId`) deferred until invitations exist.
- **Schema delta** (`auth_fields` migration): `User.passwordHash String`, `User.phone String? @unique`.

## Out of scope (future sprints)

SMS OTP (needs Twilio or similar) · email verification + password reset (needs Resend or similar) · member invitations · rate limiting / login lockout · RBAC permission enforcement beyond role seeding · refresh-token rotation.
