# Jarvis — architecture & roadmap

Multi-tenant property management. An `Organization` owns `Property` → `Unit` → `Lease`. A `User` joins an org through a `Membership`, which carries an org-scoped `Role`. Tenants are not a separate model — a lease points at the tenant's `Membership`.

## Decision log

| Date | Decision | Why |
|------|----------|-----|
| 2026-08-14 | Amount digits group **as they are typed**, and the caret is restored in a **layout effect**, never `requestAnimationFrame` | Waiting for evaluation to make `500000` readable meant the field was hardest to check exactly while it was being filled in. Grouping per keystroke is safe because the parser treats commas as separators, so it can't change the value. The caret is the whole difficulty: reformatting a controlled input drops it at the end, and the obvious `requestAnimationFrame` restore **loses the race with React's commit** — the value regrouped correctly and the caret still jumped. A layout effect reading a ref set during `onChange` runs after the DOM updates and before paint, so the caret never visibly moves. Both dialogs now share one `AmountInput` rather than two copies of this |
| 2026-08-14 | Facet options for **property** come from the rows on screen, not from `getLeaseOptions` | That helper lists every property in the org, including ones with no lease — offering them in a filter produces a guaranteed empty table, which reads as a broken filter rather than an empty set. Deriving from the data the table already holds means a facet can only ever offer something with rows behind it. Note also that a facet on a text column needs an explicit equality `filterFn`: TanStack's default is substring, so "Likely" would silently match "Likely Annex" |
| 2026-08-15 | The lease Overview is **two flex columns of equal height**, with `grow` on every card | Three shapes were tried. A 2×2 grid aligns *rows*, so Tenant (217px) beside Unit info (409px) left a measured **192px hole**. Independent columns closed the hole but staggered the two sides into a bento look. The settled shape keeps the grid's default `items-stretch` — so both column wrappers take the taller one's height — makes each wrapper a flex column, and puts **`grow`** on every card so the surplus is divided among the cards in the shorter column rather than pooling as a gap. `grow` rather than `flex-1` matters: `flex-1` resets the basis and would inflate a three-row card to match a seven-row one, where `grow` keeps content proportions and shares only the extra. Result measured at 693px per column with both bottoms at 989. **The rule: `items-stretch` + flex columns + `grow` whenever two stacks must end level; independent columns only when a ragged bottom is acceptable.** Below `lg` each wrapper is its own row, so there is no surplus and `grow` is inert |
| 2026-08-14 | ~~The lease Overview is a **2×2 card grid**~~ (superseded above), and the invoice card shows a **progress bar** instead of Total / Paid / Balance rows | Four cards where two were full-width for six short rows each: mostly empty, and it pushed the invoice below the fold. In a 2×2 every card earns its space and the `<dl>`s go single-column. The bar replaces those three rows rather than joining them — they were the same three numbers, and a reader had to subtract to see where the invoice stood. Reference, status and due date stay as rows, being facts a bar cannot carry |
| 2026-08-14 | **The evaluated sum is written into the amount input on blur, grouped with commas; no caption under the field** | User call, and the better shape: the answer belongs where the question was asked. A `= TZS 1,000,000` hint under the box meant reading two places to know what would be saved, and it stated the result without letting anyone correct it. Folding on blur puts the figure in the field, editable, and re-parses cleanly on submit because the grammar already treats commas as separators. It also removes the need to announce rounding — `500000/3` simply shows `166,667`, which is both the disclosure and the value. Per keystroke would fight the typing, so blur is the trigger. The "Up to TZS X" caption went too: the invoice card above already states the balance |
| 2026-08-14 | Both payment dialogs share **`InvoiceSummaryCard`**, and the lease's Record payment states its invoice rather than offering a picker | Record payment carried only a "Balance remaining" line while the payments page showed total, paid and balance — the same decision that unified their method pickers (Phase 33) applies to what they show above the amount. The card is shared; what differs is agency. A lease has exactly one invoice, so there is nothing to choose and the card is a read-out, which is also why `reference` is optional — it identifies a row picked out of a list and says nothing on a lease. The old "Balance remaining" header line was removed rather than kept beside the card: the same number in two places is one to keep in step and one to misread |
| 2026-08-14 | Payment amounts accept **arithmetic**, parsed by a hand-written grammar in `lib/amount-expression.ts` — never `eval` | User request: five months at 250,000 should be typed as `250000*5`, not worked out elsewhere and pasted. `eval`/`new Function` would execute arbitrary text from an input box and the app's CSP blocks them regardless, so the grammar is explicit and tiny (`+ - * / ( )`, precedence, unary minus), with `x`/`×`/`÷` and thousands separators tolerated because that is what people type. Two consequences worth remembering: **the field can no longer be `type="number"`** — a number input refuses `*` outright, so the operators were unreachable — and **anything comparing the amount must use the evaluated total**, which is what the overpayment guard got wrong at first (`Number("250000*5")` is `NaN`, so an expression skipped the check entirely). Division is rounded to whole shillings, since `Payment.amount` is an `Int`, and the hint says "rounded from …" rather than silently altering the figure. Applied to *both* payment dialogs, since they were already unified once and dividing them on how an amount is typed would repeat that mistake |
| 2026-08-13 | **Every table has a card view, and the desktop icon strip is one component (`RowActionButtons`) fed the same `RowAction[]` as the mobile sheet** | With nine tables the strip was about to be hand-written a fifth time, and row actions now exist on two surfaces at once — the shape that drifts. One component means adding an action adds it to both or neither, and the strip's spacing, sizing and accessible naming are defined once. **Users is the deliberate exception**: its members column mixes a *labelled* "Invite" button with icon buttons, and routing it through the shared renderer would flatten Invite into an unlabelled icon, so desktop keeps its hand-written column and `rowActions` is supplied for mobile alone — noted at the call site, since that is the one place two lists must be kept in step by hand. Roles gets a card but **no** `rowActions`: roles can't yet be renamed or deleted, and a button opening an empty sheet is worse than no button. Card content is chosen per entity rather than by stacking columns — units leave floor/block/tenure in the View dialog they already lived in, the Billing card drops the reference and status that every row there would repeat, and the payments card puts the invoice-status badge beside the reference rather than the tenant, because it describes the invoice and not the person |
| 2026-08-13 | **`DataTable` renders a card list under 768px**, opted into per table by supplying `renderCard` | A table narrower than its columns either scrolls sideways or crushes them, and neither is readable; cards drop to what identifies a row and what you'd act on. Opt-in rather than automatic because the card is entity-specific — there is no generic way to decide which three of eight columns matter. Wired to tenants and the member Leases tab; every other table keeps the scrolling table until someone writes its card. The switch is `useIsMobile`, which reports desktop on the server, so the first client render matches the server markup and only then swaps |
| 2026-08-13 | Mobile pagination is replaced by **progressive reveal, and the sentinel is remounted on every growth** | `key={visibleCount}` on the sentinel is the whole mechanism, not a detail: an IntersectionObserver fires on a *change* of intersection, so a sentinel still in view after a short batch never fires again and the list stalls after one load. A fresh node re-observes and fires immediately if it is still visible. Its observer lives in a **ref callback with a returned cleanup** (React 19) rather than an effect — same lifecycle, no set-state-in-effect. The reveal window resets to one batch on any filter or sort change, written from the existing change handlers. Applying a facet also scrolls to the top; **the search box deliberately does not**, since it fires per keystroke. This reveals rows already in memory — the pages hand the component the whole list — so it is not a substitute for server pagination if these tables ever grow |
| 2026-08-13 | The mobile filter sheet edits a **draft**, and **Reset leaves the search box alone** | The sheet covers the list, so applying each choice live means changing facets against results nobody can see; Apply commits, Cancel-by-dismiss discards. The draft seeds from the live filters through a `key` remount, matching the rule already used for every dialog form here. Reset clears only the facets because the search input is visible and clearable on its own — clearing it from a panel it isn't shown in reads as the list breaking. `FacetFilter` gained `label` for the same reason the sheet exists: its caption was repeating the placeholder verbatim |
| 2026-08-13 | **One `rowActions` function per table feeds both the desktop icon strip and the mobile sheet** | Row actions now exist in two places at once, which is precisely the shape that drifts — one surface quietly missing an action after a later edit. `buildTenantColumns` takes the same function `DataTable` hands its sheet and renders the icon buttons from it, so they cannot disagree. A table with no desktop actions column (the member Leases tab) passes `rowActions` for mobile alone, where there is nothing to drift from. The sheet closes *before* running an action, because most of them open a dialog and two layered overlays trap focus in the wrong one |
| 2026-08-13 | **One `AppLoader` replaces the per-route skeletons**; `components/skeletons.tsx` is deleted | User call, and the reasoning generalises: a skeleton earns its keep on a slow, uncertain wait, where holding the page's shape stops the reader losing their place and signals *what* is coming. These waits are a second or two, and at that length a dozen bespoke grey outlines flashing past read as the interface breaking rather than working. The `loading.tsx` files stay — the Suspense boundaries were always the point — and each passes its own label. The loader is built from `--stat-accent`, the same gold as the active sidebar item and the toast, so it reads as part of the app rather than a generic spinner parked inside it. **If a route ever gains a genuinely slow query, a skeleton is the right answer for that route specifically** — this decision is about the length of the wait, not a rule against skeletons |
| 2026-08-13 | Sidebar motion lives in **`sidebarMenuButtonVariants`**, names its transition properties explicitly, and is **suppressed in the collapsed icon rail** | Putting it in the shared variants means the org switcher and the user footer move the same way as the nav items, with nothing to keep in sync. `transition-all` was avoided deliberately: it would quietly ease any future `filter` or `opacity` utility someone adds to a menu button. The nudge is turned off at `group-data-[collapsible=icon]` because sliding a 32px square sideways inside a 48px rail reads as the icon coming loose rather than as a response to the pointer. `nav-pop` is keyed on `data-active`, so it fires once on the item that has just become active — CSS animations run when the name changes from none, so a re-render can't replay it |
| 2026-08-13 | Global search gained a **payment** type, and `--kind-payment` is **teal (hue 204), not rose** | Payments are scoped through `invoice.lease` with the same double org filter — the membership's *and* the unit's property's — that every other lease query uses, so the branch can't surface a row from a lease that crosses organizations (verified: all queries return 0 as the other org). The colour was forced: five kinds already sit at 36/81/155/254/300 and the standing rule is 45° minimum separation, which leaves exactly two openings, ~204 and ~348. Teal wins because a rose badge on a money row reads as a warning. Contrast measured through a canvas (`getComputedStyle` returns `lab()` here) at 5.50 light / 5.66 dark, both AA for normal text. **`TYPE_ORDER` in `global-search.tsx` had to be updated too** — it is both the section order and the filter, so a new type is invisible without it |
| 2026-08-13 | Auth-page ripples are driven entirely by **`key={pathname}`**, not by an effect | Changing the key makes React discard the old rings and mount new ones, and a CSS animation runs on mount — so there is no effect, no state, no timer to clear, and navigating again mid-ripple simply replaces the elements the first navigation was animating. Soft-edged via a radial gradient rather than a border, easing on `cubic-bezier(.22,1,.36,1)`, because most of a real disturbance's travel happens immediately and then spreads and flattens. **The form wrapper needed `relative`**: the ripple is positioned and the form was static, and a positioned element paints over a static sibling regardless of DOM order — without it the rings run across the form instead of behind it |
| 2026-08-13 | Motion is built on **`tw-animate-css` + the platform**, not a JS animation library | It was already installed and already animating every base-ui component (dialogs, dropdowns, accordion), so adding `motion` would have meant two systems covering the same ground with the shadcn components staying on the CSS one regardless. The four things asked for — skeletons, page transitions, counting figures, entering rows — are all expressible in CSS, keyframes, or one `requestAnimationFrame` loop. The honest limit, worth knowing before the next request: **CSS cannot animate an element React is unmounting**, so exit animations on our own `{open && …}` renders are not available (base-ui handles this for its own components by holding them mounted at `data-state="closed"`). Layout/FLIP reordering and gestures are the other two gaps. Reach for `motion` when one of those is actually needed, not before |
| 2026-08-13 | Page transitions wrap **only the content area**, and the group animation is turned **off** | The `<ViewTransition>` sits in `app/(app)/layout.tsx` around the content div, so the sidebar and header stay part of the untouched `root` snapshot — the fixed reference that makes it read as "the content changed" rather than "the whole app moved". `default="page"` rather than `enter`/`exit` because the boundary lives in a persistent layout: navigating within it is an *update*, since the ViewTransition instance survives and only its children swap. `::view-transition-group(.page) { animation: none }` because page heights here run from the dashboard to a four-field form, and a group interpolating between them squashes both snapshots for the whole crossing; `height: auto` on old/new then keeps each at its natural size instead of being stretched into the other's box. Verified not to disturb the theme toggle — outside a React transition the content area has no view-transition-name, so the Phase 41 circle still covers the whole page |
| 2026-08-13 | The dashboard count-up writes **`textContent` from a layout effect**, never React state | Three constraints force it. The value arrives already formatted (`formatCurrencyFull` → "TZS 900,000"), so the digits are found inside the string and put back with the same grouping/decimals/prefix/suffix rather than reimplementing `lib/format.ts`. The server must render the *final* figure, since that is what a reader without JS or with reduced motion has to see — which rules out state seeded at zero. And the reset to zero therefore has to land **before paint**, or the card shows the real figure, blinks to zero and counts back to where it already was; an ordinary `useEffect` runs after paint, a layout effect does not. Writing the DOM directly also sidesteps the set-state-in-effect rule the codebase lints for. It finishes on the server's exact string, not the eased approximation, so rounding can't leave the total a shilling short |
| 2026-08-13 | `DataTable` sets **`getRowId` from the record's id**, not the array index | TanStack's default row id is the index, which makes "row 0" a different record the instant a filter or sort changes. That is what decides whether React reuses a surviving row's DOM node or tears it down and builds another — and a rebuilt node re-runs the CSS enter animation, so every row would flash on every keystroke instead of only the ones that just appeared. Proved by tagging a row's DOM node, filtering down to it, and finding the tag intact; its animation read `finished` while the returning rows read `running`. Row selection following the record rather than the slot falls out of the same change. Falls back to the index for data with no id |
| 2026-08-09 | Font-family tokens (`--font-sans`/`--font-mono`/`--font-heading`) live **only** in `@theme inline`, pointed at the `next/font` variables directly — never in `:root`/`.dark` | Tailwind v4's `inline` theme keyword bakes a token's declared value into any utility/`@apply` using it directly, at build time, reading only the `@theme inline` declaration — a same-named override in `:root`/`.dark` further down the file **never reaches it**. Discovered because `html { @apply font-sans }` and `.font-heading` were both still resolving to shadcn's scaffold placeholders (`Inter`, and `.font-heading` → `var(--font-sans)` rather than Sora) despite the "real" per-theme values sitting unused below. Since the loaded fonts are theme-independent anyway (set once on `<html>` in `app/layout.tsx`), there was never a reason for a per-theme override to exist here — collapsing to one declaration removes the trap rather than patching around it |
| 2026-08-09 | Theme toggle animates via the **View Transitions API** — a `clip-path` circle grown from the click point via `document.startViewTransition` + `.animate()` — not a blanket CSS `transition` on every element | A global `* { transition: colors }` would also fire on hover states, table selection, and any other color change that happens to coincide with a theme switch, which reads as sluggish elsewhere for a look that only needed to exist during the toggle. The View Transitions approach is scoped entirely to the toggle's own click handler and touches nothing else. Falls back to the pre-existing instant switch under `prefers-reduced-motion` or without browser support (Firefox) — both paths verified explicitly, not assumed |
| 2026-08-12 | Auth endpoints are rate limited **in memory, keyed on IP *and* on the identifier** | Login gets 10/min per IP and 5/min per account. The per-account budget is the one that matters: keyed on IP alone, an attacker spread across addresses keeps every bucket under the limit while hammering one login. In-memory rather than Redis because nothing else here needs Redis — with the honest consequence, written into the module, that it is per process: several instances give an attacker a budget each and a deploy resets the counters. It makes online guessing slow, which is most of the value; it is not a security boundary on its own |
| 2026-08-12 | Table filters persist in a **module-level map**, not `sessionStorage` | A module map is empty on the server *and* on a fresh load, so the first render agrees on both sides — no hydration mismatch, and no `useSyncExternalStore` needed. It only holds a value after a client-side navigation, which is exactly the complaint ("I set a filter, left, came back, it was gone"). A hard reload starting clean is a feature: a remembered filter should never be a hidden reason a list looks empty. Written from the change handlers because the codebase lints against set-state-in-effect |
| 2026-08-12 | `experimental.staleTimes.dynamic = 30` — the client router cache is **on** for dynamic pages | Every page reads the session cookie, so all of them are dynamic, and Next 15 changed that default to 0: revisiting a page you were just on re-ran its queries. Measured at 4 server fetches for a four-hop cycle before, 0 after. Safe because mutations already `revalidatePath` server-side and `router.refresh()` client-side, and both evict this cache — verified by warming `/payments`, editing a lease elsewhere, and seeing the new figure on return. Also throttled `runAutoRenewals` to one sweep per org per 5 minutes; it was running a candidate query on every `/leases` and `/dashboard` render to find something that is a date-boundary event |
| 2026-08-12 | Expiry tags **escalate toward the end date** (outline inside 60 days, destructive inside 30), and the tier is decided **server-side** | The request didn't settle which tier should be sharper, so it follows the renewals panel, which already golds anything under 30 — nearer is louder, and the two surfaces now agree rather than contradicting each other. Server-side because the tables are `"use client"`: computing `Date.now()` during render gives one answer on the server and another on hydration, so a lease sitting exactly on a threshold would flicker between tiers. `leaseExpiry()` also returns null for a lease that hasn't started, since an upcoming short lease is near its end date without that meaning anything |
| 2026-08-11 | A lease stores its **own agreed `monthlyRent`**; `leaseAmount` remains the whole term's value (`monthlyRent × durationMonths`) | Rent gets negotiated away from the unit's asking price, so the lease needs its own rate. Stored rather than inferred from `leaseAmount / durationMonths`: division would recover it exactly today, but it makes the agreed rate a derived accident instead of a recorded fact, and it left the lease detail page showing `unit.rentAmount` under a "Monthly rent" label — the asking price wearing the lease's name, wrong the moment the two differ. The API field is nullish, so omitting it still means "whatever the unit asks" and no existing caller changed. Auto-renewal carries the agreed rate forward rather than repricing, since silently re-rating a negotiated lease is not a job's decision to make |
| 2026-08-10 | Editing a lease **re-derives** it from the unit's current rent, and is **refused when the new value falls below what has been paid** | `insertLease` locks the value at signing so later rent changes don't rewrite history; an edit is the opposite case — a correction of a record that was wrong — so it recomputes `endDate` and `leaseAmount` and syncs the invoice in the same transaction. The form shows the recomputed total so it can't change out of sight. The one thing an edit may not do is strand money: payments already recorded would leave an invoice mysteriously overpaid, so that edit is rejected naming both figures. **The overlap check must exclude the lease being edited** — a lease always overlaps itself, and without `id: { not: … }` no edit could ever save |
| 2026-08-10 | Derived-balance queries read **one grouped aggregate**, never a nested `payments` include | `getPayments` included `invoice.payments` per row to show invoice status, so an invoice with n payments hydrated n² payment rows — quadratic in the common case of an instalment plan. A balance can't be filtered or summed in SQL because it isn't a column, but `payment.groupBy` gets it at one row per invoice, and `getPayableInvoices` then pays for its tenant/unit joins only on the rows that survive the filter. Verified behaviour-preserving by capturing the figures in SQL before the rewrite and matching them exactly after |
| 2026-08-10 | A lease can be created from a tenant's own page, with that tenant **locked** into the form; the button is **hidden for non-tenant members** | `LeaseFormDialog` grew one optional `lockedTenantId` prop rather than a second dialog — the property→unit cascade, the minimum-tenure check and the overlap handling are all the same, and a copy would drift. Locking rather than merely pre-filling: a lease created from someone's page that quietly ended up belonging to a different tenant is a trap, not a convenience. Hiding the button for non-tenants matches the server, where `createLease` requires the Tenant role and 404s otherwise — an affordance that can only fail is worse than none |
| 2026-08-10 | **Billing totals live on the dashboard only**; the payments page is a bare ledger, and both it and the lease Billing tab present payments through the same `DataTable` | User call. Metrics were duplicated as summary cards on the payments page and as a bespoke `<Table>` in the Billing tab — two places to keep in step with the dashboard, and two payment tables that had already drifted (one had search and filters, the other didn't). The dashboard's Payments card leads with **outstanding balance** rather than collected: it's the figure that needs acting on. Its `billing` block comes from one `invoice.findMany` including payments, because a balance is derived per invoice and can't be aggregated in SQL |
| 2026-08-10 | **The invoice's figures live on the lease's Overview tab, not its Billing tab**; Billing is only the payment ledger | User call, and the split it implies is the right one: an invoice is part of what a lease *is*, so it sits with the lease terms; what has been paid against it is a log, and a log is what earns a tab. The card is deliberately a `Card` + two-column `DetailRow` `<dl>` — identical in shape to the Lease terms card directly above it — rather than the compact strip it replaced. A distinct treatment would have made it read as a transplant on a tab whose whole convention is label/value rows |
| 2026-08-10 | The payments table shows **no per-payment balance and no view button** | Two things that looked useful and weren't. The balance was the *invoice's* balance as of now, so every payment against one invoice showed the same number in a per-payment row — a figure that invites being read as "left after this payment" while meaning nothing of the sort. The eye button duplicated `getRowHref`'s double-click-to-open, which works with or without it. Deleting is now the only row action |
| 2026-08-10 | **`basis-full`, not `w-full`, is what wraps a flex child onto its own line** | The Billing tab's invoice strip truncated "TZS 750,000" to "TZS 7…" on mobile. `w-full` looked right but `flex-1` sets `flex-basis: 0`, and basis beats width in flex layout — the child shrank instead of wrapping. Only caught by looking at a 375px screenshot; the desktop layout was fine throughout |
| 2026-08-09 | Payment method is a **closed list in `lib/payment-options.ts`**, used by *both* the payments page and the lease Billing tab | The Billing tab originally took free text. Once the payments page gained a method facet filter, free text elsewhere would produce values that filter could never match — "M-Pesa", "Mpesa" and "mpesa" coexisting as three unfilterable methods. `Payment.method` stays a nullable `String` in the schema, so this constrains the form without constraining the column, same as `lib/unit-options.ts` |
| 2026-08-09 | **`lib/invoice-types.ts`** holds `InvoiceStatus`, `deriveInvoiceStatus`, `invoiceReference` and `INVOICE_STATUS_VARIANT`; `lib/invoices.ts` keeps only the Prisma-touching functions and re-exports the rest | The payments table and its dialogs need these as *runtime* values, not just types. Importing them from the Prisma-importing `lib/invoices.ts` would pull `pg` → `require('dns')` into the browser bundle and fail the build — the hazard already documented for `lib/search-types.ts` and `lib/auth/constants.ts`. **The rule for any new `lib/*` shared with a client component** |
| 2026-08-09 | Auto-renew is a **`Switch` that is disabled until a minimum tenure exists**, and clearing the tenure forces it off | The renewal job reads its term from `unit.minTenureMonths` and skips a unit without one — so a unit saved as auto-renewing with no tenure is a setting that silently does nothing. Gating the control makes that unrepresentable rather than leaving it to be discovered when a lease fails to renew. The explanatory caption was dropped as redundant once the control itself enforces the rule |
| 2026-08-09 | Billing is **one `Invoice` per `Lease`**, for the full `leaseAmount`, not recurring monthly invoices; `InvoiceStatus` (Unpaid/Partial/Paid) is **derived** from `amount` vs `Σ Payment.amount`, never stored | User decision, matching the literal request ("generate an invoice, then multiple payments over that invoice") and this codebase's existing derive-don't-store rule for `LeaseStatus`/`TenantStatus`. `createLease` now creates the `Lease` + `Invoice` atomically in `insertLease()` (`lib/leases.ts`); overpayment is rejected server-side in `lib/invoices.ts`'s `recordPayment`. Closes the `lib/dashboard.ts` decision-log item (2026-08-05) that flagged swapping lease-value derivation for real `Payment` rows once the model existed — `getDashboardStats`'s "collected" figure now sums actual payments in the year |
| 2026-08-09 | Lease auto-renewal setting is a **`Unit.autoRenew` boolean**, and it runs **lazily on page load** (`/leases`, `/dashboard`) rather than a cron endpoint | User decision on both placement (per-unit default, not per-lease or a new org-wide Settings page — this app has no settings surface at all) and trigger (no scheduler infra exists yet; matches the "derive on read" philosophy). `runAutoRenewals(organizationId)` in `lib/lease-renewal.ts` finds ended leases on auto-renewing units with no successor (`renewedTo` null) and calls the same `insertLease()` overlap-checked path `createLease` uses, so a unit someone re-let by hand between end-date and page-load can't be double-booked. Renewal duration is the unit's `minTenureMonths`; a unit with `autoRenew` on but no `minTenureMonths` set is skipped, not silently dropped. Idempotent by construction: `renewedFromId` is `@unique`, so a lease can never gain two successors. **Known gap**: a lease only renews once someone loads one of those two pages after its end date passes — no same-day guarantee |
| 2026-08-08 | Record kinds get **one `--kind-*` token each, holding the ink**; badges derive their own tint from it at 10% alpha | A tinted background composites correctly over any surface, so a single token per kind serves both themes and only its lightness is retuned in `.dark` — the alternative, a bg/fg pair per kind per theme, is four values to keep in sync and drifts. Hues are anchored to the existing palette (brand gold, the chart blues/greens/terracotta) with only violet added, so five distinguishable kinds cost almost no new colour vocabulary. **Contrast was measured, not eyeballed**: the first pass passed AA-large but failed AA text at 12px, and `getComputedStyle` returns `lab()`/`oklab()` in this browser, so any check has to resolve through a canvas to get true sRGB |
| 2026-08-08 | Every bulk importer goes through **`lib/xlsx-import.ts`** + the generic `components/import-dialog.tsx`; an entity supplies only its columns and a `toCandidate` mapper | Tenants needed the same flow as units, and the fiddly parts are entirely entity-agnostic — flattening rich-text/formula cells, matching headers loosely, skipping padding rows, catching in-file duplicates, capping rows, and suppressing schema messages the coercion pass already reported. Two copies of that would drift. The unit importer was rewritten onto it and checked against the same 9-row fixture for identical output before tenants were built on top |
| 2026-08-08 | Unit amenities are **free text**, not `z.enum(UNIT_AMENITY_OPTIONS)` | Prisma always stored `String[]`; only the schema made the list closed, so a caretaker couldn't record anything the seed list missed. The options remain as checkboxes — a starting set, not a constraint — with free entry beside them, de-duplicated case-insensitively so typing "balcony" ticks "Balcony" rather than adding a twin. ## Auth design (current sprint)

- **Credentials**: email (required, unique) or phone (optional, unique) + password. Hash with `bcryptjs` (cost 10). Zod validation, password min length 8.
- **Session**: JWT signed with `jose` HS256, secret in `AUTH_SECRET` env. Stored in httpOnly cookie: `sameSite=lax`, `secure` in prod, 7-day expiry. Payload `{ sub: userId, orgId: activeOrgId | null }`.
- **Helpers** (`lib/auth/`): `hash.ts`, `jwt.ts`, `session.ts` (`getCurrentUser()` / `requireUser()` wrapped in React `cache()`), zod schemas.
- **Flows** (route handlers): `POST /api/auth/register`, `POST /api/auth/login` (identifier resolves as email if it contains `@`, else phone), `POST /api/auth/logout`, `GET /api/auth/me`.
- **Route protection**: `proxy.ts` at repo root (Next 16's renamed middleware) redirects unauthenticated page requests to `/login` and bounces authed users off `/login`/`/register`; API routes enforce auth themselves.
- **Org creation**: happens inside registration — one `$transaction` creates `User` + `Organization` + seeds an `Owner` `Role` + `Membership`, then the session cookie is issued with that `orgId`. Org switcher (re-issue cookie with new `orgId`) deferred until invitations exist.
- **Schema delta** (`auth_fields` migration): `User.passwordHash String`, `User.phone String? @unique`.

## Out of scope (future sprints)

SMS OTP (needs Twilio or similar) · email verification + password reset (needs Resend or similar) · member invitations · rate limiting / login lockout · RBAC permission enforcement beyond role seeding · refresh-token rotation.
